# ADR-003: Engineering files live outside the database

**Status:** Accepted
**Date:** 2026-09-11

## Context

CAD models, drawings, photos, microscope images, timegrapher exports and
certificates are large, binary and numerous. They must be attachable to
any engineering entity, verifiable (did the file change?), and eventually
storable in cloud object storage. PostgreSQL is the wrong place for the
bytes and the right place for the metadata.

## Decision

* File **bytes** are written through a `FileStorage` interface
  (`nemeth/core/storage.py`) with `put`, `open`, `exists`, `delete` and
  `stat`. The first implementation is `LocalFileStorage` rooted at the
  `storage/` directory (mounted into the API container). S3 and Azure
  Blob implementations can be added later without touching callers.
* File **metadata** is a database row (`Attachment`, slice 11): original
  filename, stored key, SHA-256, MIME type, size, uploaded at/by, linked
  entity, description.
* Stored keys are generated by the server:
  `{category}/{yyyy}/{mm}/{uuid}{ext}`. Client-supplied names are recorded
  as metadata only and never used to build paths.
* The storage layer rejects absolute paths, `..` segments, and any key that
  would resolve outside its root. Uploads are validated by size and by an
  allow-list of extensions and MIME types.
* SHA-256 is computed on upload so that "did this CAD file actually
  change?" is answerable by comparing hashes.

## Consequences

* Database backups stay small; file storage is backed up as files.
* Moving to object storage is a configuration change plus one class.
* Nothing in the domain layer ever handles a filesystem path.
