# Identifier Strategy

Two kinds of identity exist for every record, and they are never confused.

| Kind | Purpose | Example | Where |
|---|---|---|---|
| **Internal ID** | Primary key, foreign keys, API paths when convenient | `9f1c2e5a-…` (UUID v4) | `id` column on every table |
| **Human identifier** | What people say, write on trays, engrave, put on drawings | `N1-MVT-002`, `EXP-014`, `N1-017` | `identifier` column, unique, immutable |

Rules:

1. Sequential database integers are never exposed. There are none: primary
   keys are UUIDs generated by the application.
2. A human identifier is assigned once and **never reused**, even if the
   record is obsoleted. Gaps are fine.
3. Human identifiers are uppercase, ASCII, and match
   `^[A-Z0-9][A-Z0-9.\-]{1,62}$`.
4. API paths accept either form: `GET /components/N1-MVT-002` and
   `GET /components/9f1c2e5a-…` return the same record. UI URLs use the
   human identifier because they are readable and stable.
5. Identifiers are generated server-side from a **counter table**
   (`identifier_counters`, one row per prefix, updated atomically). A
   client may supply its own identifier when it has a reason to; the
   server validates format and uniqueness.

## Schemes

| Entity | Pattern | Example | Prefix counter |
|---|---|---|---|
| Product | `{CODE}` | `N1` | manual |
| Product model / reference | `{PRODUCT}.{NN}` | `N1.01` | manual |
| Caliber | `CAL-{CODE}` | `CAL-N1` | manual |
| Component | `{PRODUCT}-{FAMILY}-{NNN}` | `N1-MVT-002` | `N1-MVT` |
| Component revision | `{component} Rev {LABEL}` (display only) | `N1-MVT-002 Rev C` | per component |
| Prototype | `{PRODUCT}-P{NNN}` | `N1-P003` | `N1-P` |
| Part instance | `PI-{NNNNN}` | `PI-00042` | `PI` |
| Build record | `BR-{NNNNN}` | `BR-00007` | `BR` |
| Watch | `{PRODUCT}-{NNN}` | `N1-017` | `N1` |
| Movement (serialized) *(planned)* | `{CALIBER}-{NNNN}` | `CAL-N1-0001` | `CAL-N1` |
| Experiment | `EXP-{NNN}` | `EXP-014` | `EXP` |
| Engineering change | `ECR-{NNNN}` | `ECR-0021` | `ECR` |
| Test run | `TR-{NNNNN}` | `TR-00042` | `TR` |
| Test type | `{CODE}` (uppercase, underscores) | `TIMEGRAPHER` | manual |
| Supplier | `SUP-{NNN}` | `SUP-003` | `SUP` |
| Document / attachment | `DOC-{NNNNN}` | `DOC-00108` | `DOC` |

Component families (the `{FAMILY}` segment) are a fixed vocabulary that
doubles as a filter in the UI:

| Family | Meaning |
|---|---|
| `WATCH` | Top-level watch assemblies |
| `CASE` | Case middle, bezel, crystal, crown, caseback, gaskets |
| `DIAL` | Dial, markers, printing |
| `HAND` | Hour, minute, seconds hands |
| `MVT` | Everything inside the movement, including the movement assembly itself |
| `STRAP` | Straps, bracelets, buckles |
| `PKG` | Packaging, documents delivered with the watch |
| `MISC` | Anything else |

Assemblies are numbered within their family alongside parts; the `kind`
column, not the identifier, says whether something is an assembly. Numbers
are three digits by default and grow naturally past 999.

## Revision labels

Revisions are numbered from 1 and labelled with letters in the PLM
convention: `A`–`Z`, then `AA`, `AB`, …. The number is used for ordering
and uniqueness; the label is for people. Both are stored.

## Why a counter table and not a sequence per prefix

Prefixes are open-ended (every new product and family creates one).
A row-per-prefix table with `UPDATE … RETURNING` is atomic under
concurrency, trivially inspectable, and needs no DDL when a new prefix
appears. It is also portable if the database ever changes.
